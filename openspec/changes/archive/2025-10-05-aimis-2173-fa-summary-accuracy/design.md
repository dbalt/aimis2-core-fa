# Design: AIMIS-2173 — точность саммари ФА

## Context

См. proposal.md — Why. Текущий конвейер: `summarize.py` → `build_branch_report` (TaskGroup: 2–3 LLM-запроса + детерминированная таблица) → склейка отчёта. LLM получает сырой JSON и промпты, поручающие модели арифметику (деление на scale, ×100 для ratio, выбор масштаба, группировка тысяч, смена разделителя) и свободное заполнение шаблона «Главный драйвер». Валидации вывода нет.

Доказательство работоспособности подхода «числа считает код»: таблица (`table_renderer.py`) рендерится детерминированно и во всех 5 прод-примерах ошибок в числах не содержит ни одной — в отличие от LLM-текста.

Ограничения:

- Прокси GigaChat: 1 соединение, `maxRetries=0`, без очереди; лишний параллельный запрос получает 429. Внутри прогона 3 TaskGroup-запроса — штатный прод-паттерн, сохраняем.
- SDK `sdk.giga` — внешний репозиторий aimis-sdk (editable install), не модифицируем.
- Кэш есть только на уровне `fa_server` (DataMgmt); `summarize()` вызывается напрямую — измерения харнесса не искажаются кэшем.
- `temperature` в `ask_giga` не передаётся — дефолт модели; фиксировать не будем (см. D3).
- Конфиг KeyDB `configs.fa2026.models.*` может переопределять дефолты кода (значение не проверено — см. Open Questions).

## Goals / Non-Goals

**Goals:**

- Устранить классы ошибок: выдуманные драйверы/числа у листовых узлов; потеря разрядов/неверный масштаб; 🟢 вместо ❇️; запрещённая динамика; переупаковка plan/fact в «драйвер».
- Дать LLM готовые display-строки; запретить вычисления и выдумки промптом (уровень A).
- Объективно измерить эффект: A/B — 10 независимых последовательных прогонов старый vs новый промпт, валидатор-оракул, метрики по классам ошибок.
- Дефолт `model_details`/`model_table` → `GigaChat-3-Ultra`.

**Non-Goals:**

- Runtime-валидатор в проде (только оракул в харнессе).
- Уровень B (структурный ответ LLM + рендерер чисел) — только как эскалация.
- Tool-calling для вычислений, изменения SDK/конфигов/протокола, ретраи прокси.

## Decisions

### D1. Уровень A: форматтер display-строк, LLM только цитирует

Новый модуль `src/libfa2/fa_impl/value_formatter.py`: чистая функция `data → data_display`:

- готовая строка для каждого числа: масштаб (млрд/млн/тыс/руб) по |v|, группировка тысяч пробелом, десятичная запятая, суффикс — единые правила (одна реализация; при возможности переиспользуется `table_renderer.py`);
- маркер по знаку impact (`🔴`/`❇️`) — решает код;
- флаг значимости: пороги из промптов (|impact| ≥ 30% максимального; факторы < 15% различия — включать оба) считает код, LLM выбирает только из помеченных;
- для ratio (ветка 4): пара строк «X п.п.» (impact×100) + «Y руб.» (рублёвый эквивалент) — для формулировки маржи;
- для ratio — иерархия правил из текущего промпта ветки 4 (root/прямые потомки = п.п.; глубже/срезы = абсолютные) кодифицируется в форматтере.

Вход LLM = `data_display` (те же деревья + display-строки и флаги); сырые числа остаются для контекста. Промпты: «каждое число — точная цитата строки из входа; вычисления запрещены».

**Альтернативы (отклонены):**

- *Tool-calling*: ошибка копирования числа в аргумент вызова не ловится тулзой (главный класс ошибок — разряды — остаётся); +2–4 round-trip'а на запрос через односоединённый прокси; LLM может не вызвать тулзу. 
- *Уровень B (LLM возвращает структуру, числа подставляет рендерер)*: даёт «почти ноль» ошибок, но требует рендерера фраз; принят как план эскалации, если уровень A не даст 0 ошибок в A/B.

### D2. Ревизия промптов (`summarize_prompts.py`)

- `_BASE_FACTORS`: EDGE CASE для листовых узлов — «Главный драйвер» только если у узла есть дети в JSON; запрет причинно-следственных оборотов, не выводимых из имён узлов; запрет переупаковки plan/fact узла в «драйвер»; снятие конфликта «count how many axis blocks… must be in the output» vs «IF TREE HAS NO CHILDREN — DONT MENTION IT» (блоков может быть меньше, чем осей).
- Все ветки: числа — только цитаты display-строк; маркеры/знаки — из display-данных; строго ❇️/🔴; запрет слов динамики.
- Ветка 4: обязательный шаблон «отклонение маржи составило {X п.п.}, что оказало влияние на верхнеуровневый показатель в {Y руб.}» — подстановка готовой пары.
- `_KEY_FACTORS_BRANCH_2`: удалить 执行.
- Отбор факторов: только узлы с `significant: true`.
- Старые версии промптов сохраняются в коде как `*_LEGACY` — для A/B-харнесса; удаляются по завершении change.

### D3. A/B-харнесс (adhoc, база — `adhoc__make_summaries_from_jsons.py`)

```
для каждой фикстуры из tmp/json/:
  для variant in [legacy, new]:
    для run in 1..10:                 # 10 НЕЗАВИСИМЫХ генераций
      summarize(data, get_llm_client) # прод-путь, temperature по умолчанию
        → валидатор-оракул → лог ошибок
      # прогоны строго последовательно, синхронно
  → сводная метрика: fixture × variant × класс ошибки → счётчик
```

- 10 прогонов = 10 разных генераций (temperature по умолчанию, кэша нет) — измеряем частоту ошибок, не детерминизм.
- Параллельность только штатная (3 TaskGroup-запроса внутри прогона); между прогонами — последовательно; при 429 — пауза (конфиг харнесса).
- Переключение промптов: явная параметризация (`summarize`/`build_branch_report` принимают набор промптов с дефолтом на `SummarizerPrompt`) — предпочтительно против monkeypatch.
- Клиент: ген-функция с кэшированием одного клиента (сейчас `summarize` создаёт 3 клиента на отчёт — лишние handshake'и при 60+ вызовах).
- Валидатор-оракул — чистая функция, unit-тестируется: числа ∈ множеству display-строк (допуск на эквивалентные написания той же величины), имена ⊆ узлам JSON, маркер ↔ знак, отсутствие слов динамики, строго ❇️/🔴. Ошибки классифицируются (таксономия ниже).
- Выход: `tmp/reports/{fixture}__{variant}__run{i}.md` + `tmp/ab_report.json` + сводная таблица в stdout.
- Критерий приёмки: новый промпт — 0 ошибок во всех прогонах × всех фикстурах. При провале — правка промпта и повторный прогон (итерация дешёвая, кроме токенов).
- Все прогоны (legacy и new) на одной модели `GigaChat-3-Ultra` — иначе сравнение загрязнено сменой модели.

### D4. Замена дефолтов модели

`GigaChat-2-Max` → `GigaChat-3-Ultra`: `run__fa_server.py` (fallback `get_conf('configs.fa2026.models.details', ...)`), `fa_server.py:27`, `summarize.py` (дефолты `llm_model`/`model_table`/`model_details`), `all_together.py:25`. SDK (`DEFAULT_GIGA_MODEL`) и KeyDB-конфиг не трогаем.

## Таксономия ошибок валидатора (из анализа 5 SQL-примеров)

| Класс | Пример из прод-данных |
|---|---|
| `INVENTED_NUMBER` | «−986,74 млн» при отсутствии числа в JSON |
| `INVENTED_FACTOR` | «чистые процентные доходы» у листа без детей |
| `WRONG_SCALE` | «1 105 млн» вместо 11 047,2 млн; «29213 млн» вместо «29213 млрд» |
| `INVENTED_DRIVER` | «рост страховых выплат (−6 190,72)» без детей у узла |
| `WRONG_MARKER` | 🟢 вместо ❇️; маркер не совпадает со знаком |
| `DYNAMICS_LANGUAGE` | «рост», «снижение», «опережающего роста» |
| `UNALLOWED_NAME` | имя фактора отсутствует в JSON |
| `REPACKED_PLAN_FACT` | plan/fact узла выдан за «драйвер» |

## Risks / Trade-offs

- **Промпт — не гарантия** (LLM может неточно цитировать строку) → display-строки максимально «копипастабельны»; оракул покажет остаточную частоту; при недостижении 0 — эскалация к уровню B (отдельное решение).
- **Оракул ложно/неполно парсит корректный вывод** → допуск на эквивалентные форматы; red-тесты: 5 SQL-примеров обязаны ловиться, чистые — проходить; ручная сверка первых прогонов.
- **429 от прокси при прогонах** → последовательные прогоны, пауза, кэшированный клиент; при массовых 429 — снижение параллельности внутри прогона (отклонение от прод-пути фиксируем в отчёте).
- **KeyDB-конфиг переопределяет дефолт — замена модели в коде не сработает** → проверить значение `configs.fa2026.models.details` при имплементации; если задан — зафиксировать обновление конфига отдельной задачей.
- **Стоимость/время A/B** (~2 варианта × 10 прогонов × K фикстур × 2–3 запроса; на 3 фикстурах ~120–180 запросов) → фикстуры от заказчика; при необходимости сократить до 5 прогонов — решение фиксируется в tasks.

## Migration Plan

1. Форматтер + unit-тесты (вкл. red-кейс «29213553» от заказчика).
2. Ревизия промптов (legacy-версии сохраняются в коде для харнесса).
3. Харнесс + валидатор-оракул; фикстуры от заказчика; прогон A/B; итерации промпта до 0 ошибок.
4. Замена дефолтов модели; чистка 执行.
5. Откат: revert коммитов; legacy-промпты и харнесс удаляются по завершении change.

## Open Questions
