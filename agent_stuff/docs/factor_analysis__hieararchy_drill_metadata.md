# Метаданные иерархии показателей для факторного анализа

## Описание

Метаданные описывают иерархическую структуру финансовых показателей, используемую для факторного анализа отклонений факта от плана. Иерархия представлена в виде плоского списка узлов, где связи между узлами устанавливаются через поле `parent`.

### Основные концепции

- **Узел иерархии** — отдельный JSON-объект, описывающий один финансовый показатель
- **Корневой узел** — показатель верхнего уровня, не имеет `parent`
- **Листовой узел** — показатель, не имеющий дочерних элементов (потомков)
- **Составной узел** — показатель, значение которого вычисляется из дочерних компонентов
- **Собираемый показатель** — показатель, значения плана/факта которого можно получить напрямую из БД (имеет поле `query`)

### Типы составных показателей

| Тип | Описание | Формула |
|-----|----------|---------|
| `sum` | Суммируемые компоненты | parent = child1 + child2 + ... + childN |
| `multi` | Компоненты-множители | parent = rate x base |
| `ratio` | Показатель типа отношение | parent = numerator / denominator (только корень) |

### Правила

1. Каждый узел имеет уникальные `id` (int) и `code` (string)
2. Корневой узел не имеет поля `parent`, листовые узлы не имеют поля `type`
3. Показатели типа `multi` **обязательно** должны иметь поле `query` (ставка считается обратным счетом)
4. Показатели без `query` вычисляются суммированием потомков (если тип `sum` и сабтотал не хранится в БД)
5. Показатели типа `ratio` размещаются **только** на корневом уровне
6. Дочерние элементы `multi` узла должны содержать поле `multiplierType`: `rate` (множитель) или `base` (база)
7. Для `ratio` узла указываются ссылки на `numerator` (числитель) и `denominator` (знаменатель) через их ID

## Структура JSON

### Корневой элемент

```json
{
  "metrics": [...]
}
```

### Объект узла иерархии (MetricNode)

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `id` | int | Да | Уникальный числовой идентификатор показателя |
| `code` | string | Да | Краткий мнемонический код показателя |
| `name` | string | Да | Отображаемое имя показателя |
| `parent` | int | Нет | ID родительского показателя. Отсутствует для корневого узла |
| `type` | string | Нет | Тип составного показателя: `"sum"`, `"multi"` или `"ratio"`. Отсутствует для листовых узлов |
| `query` | object | Нет | Параметры запроса к БД для получения значений плана/факта |
| `multiplierType` | string | Нет | Тип компонента-множителя: `"rate"` или `"base"`. Только для потомков узлов типа `multi` |
| `numerator` | int | Нет | ID показателя-числителя. Только для узлов типа `ratio` |
| `denominator` | int | Нет | ID показателя-знаменателя. Только для узлов типа `ratio` |

### Объект параметров запроса (Query)

Словарь, где ключ — имя поля в БД, значение — строка или массив строк для фильтрации:

```json
{
  "<fieldName>": "<fieldValue>" | ["<value1>", "<value2>", ...]
}
```

## Полная схема JSON

```json
{
  "metrics": [
    {
      "id": 1,                              // Уникальный ID
      "code": "NET_INT_INC",                // Мнемонический код
      "name": "Чистый процентный доход",     // Отображаемое имя
      "type": "sum",                         // Тип: sum | multi | ratio (отсутствует для листьев)
      // "parent": null,                    // Отсутствует для корня
      // "query": {...},                    // Параметры запроса (если собираем из БД)
      // "multiplierType": "rate"|"base",   // Только для детей multi
      // "numerator": 10,                   // Только для ratio
      // "denominator": 20                  // Только для ratio
    }
  ]
}
```

## Пример 1: Суммируемые показатели (sum)

Иерархия чистого процентного дохода, где все компоненты складываются:

```
Чистый процентный доход (sum)
├── Процентный доход
│   ├── Процентный доход по кредитам
│   └── Процентный доход по ценным бумагам
├── Процентный расход
│   ├── Процентный расход по выпускам
│   └── Процентный расход по депозитам
└── Прочие компоненты ЧПД
```

```json
{
  "metrics": [
    {
      "id": 1,
      "code": "NET_INT_INC",
      "name": "Чистый процентный доход",
      "type": "sum"
    },
    {
      "id": 10,
      "code": "INT_INC",
      "name": "Процентный доход",
      "parent": 1,
      "type": "sum"
    },
    {
      "id": 101,
      "code": "INT_INC_LOANS",
      "name": "Процентный доход по кредитам",
      "parent": 10,
      "query": {"metric_type": "interest_income", "product_group": ["corporate_loans", "retail_loans", "sme_loans"]}
    },
    {
      "id": 102,
      "code": "INT_INC_SECURITIES",
      "name": "Процентный доход по ценным бумагам",
      "parent": 10,
      "query": {"metric_type": "interest_income", "product_group": "securities"}
    },
    {
      "id": 20,
      "code": "INT_EXP",
      "name": "Процентный расход",
      "parent": 1,
      "type": "sum"
    },
    {
      "id": 201,
      "code": "INT_EXP_ISSUES",
      "name": "Процентный расход по выпускам",
      "parent": 20,
      "query": {"metric_type": "interest_expense", "product_group": "issues"}
    },
    {
      "id": 202,
      "code": "INT_EXP_DEPOSITS",
      "name": "Процентный расход по депозитам",
      "parent": 20,
      "query": {"metric_type": "interest_expense", "product_group": ["current_accounts", "term_deposits"]}
    },
    {
      "id": 30,
      "code": "NET_INT_INC_OTHER",
      "name": "Прочие компоненты ЧПД",
      "parent": 1,
      "query": {"metric_type": "interest_other"}
    }
  ]
}
```

**Пояснение:**
- Корень `NET_INT_INC` (id: 1) — тип `sum`, значение = сумма потомков (10 + 20 + 30)
- Промежуточные узлы `INT_INC` (id: 10) и `INT_EXP` (id: 20) — тип `sum`, значение = сумма потомков
- Листовые узлы (101, 102, 201, 202, 30) — имеют `query`, значения берутся из БД
- Узлы без `query` вычисляются суммированием дочерних элементов

## Пример 2: Компоненты-множители (multi)

Иерархия, где показатель рассчитывается как произведение ставки на объем:

```
Процентный доход (multi, query обязателен)
├── Ставка процентного дохода (rate)
└── Объем требований (base)
```

```json
{
  "metrics": [
    {
      "id": 100,
      "code": "INT_INC_RATE_BASE",
      "name": "Процентный доход",
      "type": "multi",
      "query": {"metric_type": "interest_income"}
    },
    {
      "id": 110,
      "code": "INT_INC_RATE",
      "name": "Ставка процентного дохода",
      "parent": 100,
      "multiplierType": "rate"
    },
    {
      "id": 120,
      "code": "INT_INC_VOLUME",
      "name": "Объем требований по долговым фин. инструментам",
      "parent": 100,
      "multiplierType": "base",
      "query": {"metric_type": "interest_income_volume"}
    }
  ]
}
```

**Пояснение:**
- Корень `INT_INC_RATE_BASE` (id: 100) — тип `multi`, **обязательно** имеет `query`
  - Значение (план/факт) берется из БД по `query`
  - Ставка (`rate`) вычисляется обратным счетом: rate = parent / base
- Дочерний узел `INT_INC_RATE` (id: 110) — тип компонента `rate`
  - Не имеет собственного `query` — значение ставки рассчитывается: rate = INT_INC_RATE_BASE / INT_INC_VOLUME
- Дочерний узел `INT_INC_VOLUME` (id: 120) — тип компонента `base`
  - Имеет `query` — значение объема берется из БД

**Формула:** Процентный доход = Ставка x Объем

## Пример 3: Смешанная иерархия (sum + multi)

Реалистичный пример, сочетающий суммируемые и мультипликативные компоненты:

```
Чистый процентный доход (sum)
├── Процентный доход (multi)
│   ├── Ставка процентного дохода (rate)
│   └── Объем требований (base)
├── Процентный расход (multi)
│   ├── Ставка процентного расхода (rate)
│   └── Объем обязательств (base)
└── Прочие компоненты ЧПД (leaf)
```

```json
{
  "metrics": [
    {
      "id": 1,
      "code": "NET_INT_INC",
      "name": "Чистый процентный доход",
      "type": "sum"
    },
    {
      "id": 10,
      "code": "INT_INC",
      "name": "Процентный доход",
      "parent": 1,
      "type": "multi",
      "query": {"metric_type": "interest_income"}
    },
    {
      "id": 11,
      "code": "INT_INC_RATE",
      "name": "Ставка процентного дохода",
      "parent": 10,
      "multiplierType": "rate"
    },
    {
      "id": 12,
      "code": "INT_INC_VOLUME",
      "name": "Объем требований по долговым фин. инструментам",
      "parent": 10,
      "multiplierType": "base",
      "query": {"metric_type": "interest_income_volume"}
    },
    {
      "id": 20,
      "code": "INT_EXP",
      "name": "Процентный расход",
      "parent": 1,
      "type": "multi",
      "query": {"metric_type": "interest_expense"}
    },
    {
      "id": 21,
      "code": "INT_EXP_RATE",
      "name": "Ставка процентного расхода",
      "parent": 20,
      "multiplierType": "rate"
    },
    {
      "id": 22,
      "code": "INT_EXP_VOLUME",
      "name": "Объем обязательств по долговым фин. инструментам",
      "parent": 20,
      "multiplierType": "base",
      "query": {"metric_type": "interest_expense_volume"}
    },
    {
      "id": 30,
      "code": "NET_INT_INC_OTHER",
      "name": "Прочие компоненты, включенные в ЧПД",
      "parent": 1,
      "query": {"metric_type": "interest_income_other"}
    }
  ]
}
```

**Пояснение:**
- `NET_INT_INC` = `INT_INC` + `INT_EXP` + `NET_INT_INC_OTHER` (суммирование)
- `INT_INC` = Ставка x Объем (множители)
- `INT_EXP` = Ставка x Объем (множители)
- Ставки (id: 11, 21) рассчитываются обратным счетом: rate = parent / base

## Пример 4: Показатель типа ratio (COR)

Иерархия показателя COR (Cost of Risk) — отношение расходов на резервы к работающим активам:

```
COR (ratio) = Расходы на резервы (numerator) / Работающие активы (denominator)

Расходы на резервы (sum, numerator)
├── Резервы по корпоративным кредитам
├── Резервы по розничным кредитам
└── Резервы по кредитам МСБ

Работающие активы (sum, denominator)
├── Кредитный портфель (multi)
│   ├── Ставка кредитного портфеля (rate)
│   └── Объем кредитного портфеля (base)
└── Прочие работающие активы
```

```json
{
  "metrics": [
    {
      "id": 1,
      "code": "COR",
      "name": "COR (Cost of Risk)",
      "type": "ratio",
      "numerator": 10,
      "denominator": 20
    },
    {
      "id": 10,
      "code": "RESERVE_EXPENSE",
      "name": "Расходы на резервы",
      "type": "sum"
    },
    {
      "id": 101,
      "code": "RES_CORP",
      "name": "Резервы по корпоративным кредитам",
      "parent": 10,
      "query": {"metric_type": "reserve_expense", "product_group": "corporate_loans"}
    },
    {
      "id": 102,
      "code": "RES_RETAIL",
      "name": "Резервы по розничным кредитам",
      "parent": 10,
      "query": {"metric_type": "reserve_expense", "product_group": "retail_loans"}
    },
    {
      "id": 103,
      "code": "RES_SME",
      "name": "Резервы по кредитам МСБ",
      "parent": 10,
      "query": {"metric_type": "reserve_expense", "product_group": "sme_loans"}
    },
    {
      "id": 20,
      "code": "WORKING_ASSETS",
      "name": "Среднехронологические работающие активы",
      "type": "sum"
    },
    {
      "id": 201,
      "code": "CREDIT_PORTFOLIO",
      "name": "Кредитный портфель",
      "parent": 20,
      "type": "multi",
      "query": {"metric_type": "credit_portfolio"}
    },
    {
      "id": 2011,
      "code": "CREDIT_PORTFOLIO_RATE",
      "name": "Ставка кредитного портфеля",
      "parent": 201,
      "multiplierType": "rate"
    },
    {
      "id": 2012,
      "code": "CREDIT_PORTFOLIO_VOLUME",
      "name": "Объем кредитного портфеля",
      "parent": 201,
      "multiplierType": "base",
      "query": {"metric_type": "credit_portfolio_volume"}
    },
    {
      "id": 202,
      "code": "OTHER_WORKING_ASSETS",
      "name": "Прочие работающие активы",
      "parent": 20,
      "query": {"metric_type": "other_working_assets"}
    }
  ]
}
```

**Пояснение:**
- `COR` (id: 1) — корневой узел типа `ratio`, не имеет `parent`
  - `numerator`: 10 (Расходы на резервы)
  - `denominator`: 20 (Работающие активы)
  - COR = Расходы на резервы / Работающие активы
- Числитель `RESERVE_EXPENSE` (id: 10) — сам является корнем своей подиерархии (parent отсутствует), тип `sum`
  - Его потомки (101, 102, 103) — листовые узлы с `query`, значения из БД
  - Значение числителя = сумма потомков
- Знаменатель `WORKING_ASSETS` (id: 20) — сам является корнем своей подиерархии (parent отсутствует), тип `sum`
  - Включает вложенный `multi` узел `CREDIT_PORTFOLIO` (id: 201) со своими rate/base потомками
  - Значение знаменателя = Кредитный портфель + Прочие активы
- Итоговая иерархия имеет 3 корневых узла (1, 10, 20), что допустимо для структуры ratio

## Примечания

1. **Плоская структура** — все узлы хранятся в одном массиве `metrics`, связи устанавливаются через `parent`
2. **Уникальность** — `id` и `code` уникальны в пределах одной иерархии
3. **Query для multi** — показатель типа `multi` обязан иметь `query`, т.к. ставка (rate) вычисляется обратным счетом: rate = parent_value / base_value
4. **Сабтоталы** — если промежуточное значение хранится в БД, узел может иметь `query` даже при наличии потомков
5. **Ratio на корне** — показатель `ratio` всегда является корневым, числитель и знаменатель — отдельные поддеревья
6. **Совместимость** — структура JSON соответствует формату сериализации/десериализации классов `Hierarchy` и `MetricNode` из модуля `libfa2.hier_metadata`
