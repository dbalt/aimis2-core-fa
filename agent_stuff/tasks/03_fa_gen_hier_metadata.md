Проанализируй @agent_stuff/docs/factor_analysis__general_description.md, раздел 1

Предложи вариант структуры хранения метаданных об иерарархии показателей в формате JSON

доп инфа:

каждый показатель со своей иерархией, аналитическими разрезами и значениями плана и факта + отчетная дата, все лежат в одной таблице БД

- каждый узел иерархии показателей описывается с помощью отдельного json object

- у каждого показателя должен быть parent и cildren (у корня нет parent у листьев нет children). 

- У каждого показателя должен быть id (int), code и name (отображаемое имя)

- Показатель может быть собираем напрямую из БД или нет. Если он собираем из БД, то у него должно быть свойство query в котором будут описаны параметры запроса (например в формате {<fieldName>:<fieldVal> or [<listOfFieldVals>], ...})

- Если показатель составной (не является листом иерархии), то у него должно быть поле type: sum для состоящих из суммируемых, multi для состоящего из множителей и ratio для показателя типа отношение 

- Для компонент - множителей нужно указать тип компонента: rate или base (componentMultiPartType)

- Компоненты из которых состоит показатель отношение могут быть либо числителем (numerator) либо знаменателем (denominator), тип должен быть указан в поле componentRatioPartType

Сгенерируй описание в структурированном и понятном формате, также сгенерируй пример в котором есть и суммируемые показатели и состоящие из множителей и также показатели типа ratio (можно отдельными примерами).


_Если показатель не собираем из БД напрямую - это значит что его можно собрать суммированием его потомков. Обычно в БД не хранятся сабтоталы на всех уровнях иерархии. Но это не обязательное требование, сабтоталы могут присутствовать и тогда этим надо пользоваться_

_еще необходимо учесть, что показатели типа multi обязательно должны быть собираемы из БД, поскольку один из драйверов (ставка) считается обратным счетом_
