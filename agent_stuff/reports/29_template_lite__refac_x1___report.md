# Отчёт по задаче 29: Рефакторинг формирования аналитической структуры (`adhoc.template_lite`)

## Суть изменения

Изменён способ, которым `_build_analyt_metadata` строит `AnalyticalStructureMetadata`
для узлов-разрезов (`NodeRole.RAZREZ`):

- **Было:** каждый разрез превращался в **отдельный `Algorithm`** (по алгоритму на
  разрез), у каждого — одношаговый `drill_order=[[<code>]]`.
- **Стало:** все разрезы одного `MetricNode` попадают в **один-единственный
  `Algorithm`** с `id=1`, образуя цепочку шагов в `drill_order` (по одному коду
  измерения на шаг, в порядке разрезов исходного сценария).

Это соответствует семантике предметной области: несколько разрезов одного показателя
— это **одна последовательность детализации** (один порядок разложения), а не
несколько независимых алгоритмов (см. `factor_analysis__general_description.md`,
раздел «Разложение по аналитическим разрезам» — «Порядок разложения»).

## Что менялось

### [src/adhoc/template_lite/transform.py](src/adhoc/template_lite/transform.py)

1. **`_build_analyt_metadata`** — основная правка:
   - измерения (`Dimension`) по-прежнему добавляются по одному на разрез с прежней
     обработкой коллизий через `_unique_dimension_code`;
   - коды собираются в список `codes` (в порядке разрезов);
   - вместо `add_algorithm` внутри цикла строится **один** алгоритм:
     `Algorithm(id=1, drill_order=[[code] for code in codes])`.
   - обновлён docstring с описанием нового поведения и обоснованием семантики.

2. **Модульный docstring (правило 1)** — уточнён: теперь явно сказано, что все
   разрезы показателя образуют один алгоритм с цепочкой шагов в `drill_order`.

3. **Комментарий у вызова `_build_analyt_metadata`** в
   `transform_template_lite_to_hierarchy` — уточнён (один алгоритм, `None` при
   отсутствии разрезов).

### Логирование (требование задачи 28)

- `get_logger()` — в начале метода (как и было).
- `lgr.debug(...)` — трейс входного списка разрезов и итоговых значений
  (измерений, алгоритмов, `drill_order`).
- `lgr.info(...)` — добавлен на ключевой развилке: сколько разрезов сгруппировано
  и что построен один алгоритм с N шагами.
- `lgr.warning(...)` — в `_unique_dimension_code` при коллизии кодов (без изменений).

## Поведение по числу разрезов

| Кол-во разрезов | Измерений | Алгоритмов | `drill_order` |
|---|---|---|---|
| 0 | 0 | — (`None`) | — |
| 1 | 1 | 1 | `[[code]]` |
| 2 | 2 | 1 | `[[code1], [code2]]` |
| N | N | 1 | `[[code1], …, [codeN]]` |

Порядок шагов определяется порядком обхода узлов (уже детерминирован по `id` узла
в `razrez_by_target`).
