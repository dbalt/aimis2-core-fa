### 2. Формулирование требований к структуре таблицы

На основе анализа метаданных были определены требования к таблице базы данных.

#### Анализ источников столбцов таблицы:

1. **Из метаданных иерархии (свойство `query`):**
   - Поле `metric` — используется для идентификации конкретного показателя в таблице БД
   - Это единственное поле, которое встречается в ключах свойства `query` в примерах метаданных

2. **Из метаданных аналитических разрезов (свойство `column`):**
   - Для упрощения в примере принято, что свойство `column` равно `code` для каждого разреза
   - `segment` — идентификатор сегмента
   - `geo_structure` — идентификатор геоструктуры
   - `product` — идентификатор продукта

3. **Обязательные столбцы:**
   - Отчетная дата: `rep_dt`
   - Значение плана: `val_plan`
   - Значение факта: `val_fact`

#### Итоговая структура таблицы (после уточнений):

| Столбец | Тип данных | Обязательный | Описание |
|---------|-----------|--------------|----------|
| `metric` | varchar(50) | Да | Тип метрики (соответствует полю `metric` в свойстве `query`) |
| `rep_dt` | date | Да | Отчетная дата |
| `val_plan` | decimal(18, 6) | Да | Значение плана |
| `val_fact` | decimal(18, 6) | Да | Значение факта |
| `segment` | varchar(50) | Да | Идентификатор сегмента |
| `geo_structure` | varchar(50) | Да | Идентификатор геоструктуры |
| `product` | varchar(50) | Да | Идентификатор продукта |

#### Удаленные поля (по результату уточнений):

- `id` — уникальный идентификатор записи (не требуется)
- `indicator_code` — код показателя (заменен на `metric`)
- `indicator_id` — ID показателя (не требуется)
- `channel_id` — идентификатор канала продаж (неактуально для примера)
- `client_type_id` — идентификатор типа клиента (неактуально для примера)
- `currency_code` — код валюты (неактуально для примера)
- `created_at` — дата создания записи (не требуется)
- `updated_at` — дата обновления записи (не требуется)

### 3. Генерация примера таблицы с данными

Был создан пример таблицы `fa_indicator_data` с реалистичными данными для:
- Метрика: "Комиссионный доход" (metric: "commission_income_total")
- Уровень детализации: Сегмент + Геоструктура + Продукт (самый детальный уровень)
- Отчетная дата: 2026-04-01

Пример содержит:
- 15 записей с самым детальным уровнем (сегмент + геоструктура + продукт)
- Отсутствуют тоталы и сабтоталы — все агрегации выполняются программно
- Разложение по сегментам и геоструктурам рассчитывается через GROUP BY

Данные комплементарны примерам из документации и демонстрируют отклонения факта от плана:
- Общий итог: план 1000.00 → факт 900.00 (отклонение -100.00)
- Юридические лица: план 600.00 → факт 650.00 (+50.00) — план выполнен
- Физические лица: план 300.00 → факт 200.00 (-100.00) — план не выполнен
- Прочие: план 100.00 → факт 50.00 (-50.00) — план не выполнен

Также были добавлены примеры SQL-запросов для разных уровней детализации с использованием GROUP BY.

## Выводы

1. Структура таблицы должна поддерживать:
   - Хранение только самых детализированных данных
   - Фильтрацию по полю `metric` для идентификации конкретного показателя
   - Отсутствие NULL значений во всех столбцах
   - Отсутствие тоталов и сабтоталов — рассчитываются программно

2. Гибкость структуры:
   - Возможность добавления новых аналитических разрезов без изменения существующих столбцов
   - Поддержка различных типов показателей (sum, multi, ratio)
   - Минимальный набор обязательных полей обеспечивает простоту структуры

3. Масштабируемость:
   - Предложенные индексы обеспечивают эффективность запросов для различных сценариев разложения
   - Композитный индекс оптимизирует запросы с фильтрацией по нескольким разрезам одновременно
   - Хранение только детализированных данных уменьшает объем хранилища

4. Архитектурные преимущества:
   - Источник истины — только детализированные данные
   - Нет риска рассинхронизации между детализированными и агрегированными данными
   - Гибкость — тоталы любого уровня могут быть получены через GROUP BY
   - Простота поддержания консистентности данных
