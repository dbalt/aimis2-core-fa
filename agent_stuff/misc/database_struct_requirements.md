# Требования к структуре таблицы базы данных для факторного анализа

## Краткое описание структуры метаданных

### Метаданные иерархии показателей

Метаданные иерархии описывают древовидную структуру финансовых показателей, где каждый узел может быть:
- **Листом** — показатель, получаемый напрямую из БД
- **Составным узлом** — показатель, рассчитываемый из дочерних компонентов

**Типы составных узлов:**
- `sum` — сумма дочерних компонентов
- `multi` — произведение множителя (rate) на базу (base)
- `ratio` — отношение числителя к знаменателю (только для корневого показателя)

**Пример метаданных иерархии:**
```json
{
  "id": 10,
  "code": "NII",
  "name": "Чистый процентный доход",
  "parent": 1,
  "type": "sum"
},
{
  "id": 101,
  "code": "INT_INC",
  "name": "Процентный доход",
  "parent": 10,
  "type": "multi",
  "query": {
    "metric": "interest_income"
  }
}
```

Для собираемых из БД показателей указывается свойство `query` с параметрами фильтрации. Для определения конкретного показателя в таблице БД используется поле `metric` из свойства `query` (__в данном примере__).


### Метаданные разложения по аналитическим разрезам

Метаданные описывают алгоритмы разворота значений показателей по аналитическим измерениям:
- Сегмент (segment)
- Геоструктура (geo_structure)
- Продукт (product)


Каждый алгоритм определяет порядок последовательной детализации данных. Таблица хранит только самые детализированные данные, а тоталы и сабтоталы рассчитываются программно.

**Пример метаданных аналитических разрезов:**
```json
{
  "algorithms": [
    {
      "id": 1,
      "drill_order": [
        ["segment"],
        ["geo_structure"],
        ["product"]
      ]
    }
  ],
  "dimensions": [
    {
      "code": "segment",
      "name": "Сегмент",
      "column": "segment"
    },
    {
      "code": "geo_structure",
      "name": "Геоструктура",
      "column": "geo_structure"
    },
    {
      "code": "product",
      "name": "Продукт",
      "column": "product"
    }
  ]
}
```

## Требования к таблице

### Структура таблицы `fa_indicator_data`

В контексте обеспечения данными в рамках описанного примера, нужна таблица такой структуры:

| Столбец | Тип данных | Обязательный | Описание |
|---------|-----------|--------------|----------|
| `metric` | varchar(50) | Да | Тип метрики (соответствует полю `metric` в свойстве `query` метаданных иерархии) |
| `rep_dt` | date | Да | Отчетная дата |
| `val_plan` | decimal(18, 6) | Да | Значение плана |
| `val_fact` | decimal(18, 6) | Да | Значение факта |
| `segment` | varchar(50) | Да | Идентификатор сегмента |
| `geo_structure` | varchar(50) | Да | Идентификатор геоструктуры |
| `product` | varchar(50) | Да | Идентификатор продукта |

## Принцип формирования минимального набора столбцов

### Общий алгоритм

Для формирования минимального набора столбцов таблицы на основе набора метаданных иерархии и аналитической структуры необходимо:

1. **Выявить обязательные столбцы** — присутствуют в любой конфигурации
2. **Выявить столбцы аналитических разрезов** — из метаданных алгоритмов разложения
3. **Выявить дополнительные фильтры** — из свойств `query` в метаданных иерархии
4. **Объединить требования от всех показателей** — взять объединение всех необходимых столбцов

### Шаг 1: Выявление обязательных столбцов

Следующие столбцы являются обязательными для любого набора показателей:

| Столбец | Обоснование |
|---------|------------|
| `metric` | Используется для идентификации показателя (встречается в `query` метаданных иерархии) |
| `rep_dt` | Отчетная дата — обязательное измерение для всех показателей |
| `val_plan` | Значение плана — обязательное поле для факторного анализа |
| `val_fact` | Значение факта — обязательное поле для факторного анализа |

### Шаг 2: Выявление столбцов аналитических разрезов

Столбцы аналитических разрезов берутся из поля `dimensions` в метаданных алгоритмов разложения.

Для каждого разреза добавляется столбец с именем, указанным в свойстве `column`:

```json
"dimensions": [
  {
    "code": "segment",
    "name": "Сегмент",
    "column": "segment"  // Добавляется столбец "segment"
  },
  {
    "code": "geo_structure",
    "name": "Геоструктура",
    "column": "geo_structure"  // Добавляется столбец "geo_structure"
  }
]
```

**Правило:** В таблицу добавляются ВСЕ разрезы из `dimensions`, даже если конкретный алгоритм использует их не все. Это обеспечивает гибкость для разных алгоритмов разложения.

### Шаг 3: Выявление дополнительных фильтров

Дополнительные столбцы для фильтрации могут быть указаны в свойствах `query` метаданных иерархии.

**Пример с фильтром:**
```json
{
  "id": 101,
  "code": "INT_INC",
  "name": "Процентный доход",
  "type": "multi",
  "query": {
    "metric": "interest_income",
    "currency": "RUB"  // Добавляется столбец "currency"
  }
}
```

**Правило:** Если в `query` встречаются ключи, не соответствующие столбцам аналитических разрезов, они добавляются как дополнительные фильтры.

### Шаг 4: Объединение требований от нескольких показателей

При наличии нескольких показателей берется **объединение** (union) всех необходимых столбцов.

**Пример:**
- Показатель A использует разрезы: segment, geo_structure
- Показатель B использует разрезы: segment, product
- Показатель C использует фильтр: currency

**Итоговый набор столбцов:**
```
metric, rep_dt, val_plan, val_fact,
segment, geo_structure, product,
currency
```

### Пример для нескольких показателей

#### Метаданные иерархии

```json
[
  // Показатель 1: Комиссионный доход
  {
    "id": 20,
    "code": "COMM_INC",
    "name": "Комиссионный доход",
    "type": "sum",
    "query": {
      "metric": "commission_income_total"
    }
  },

  // Показатель 2: Процентный доход
  {
    "id": 101,
    "code": "INT_INC",
    "name": "Процентный доход",
    "type": "multi",
    "query": {
      "metric": "interest_income",
      "currency": "RUB"
    }
  },

  // Показатель 3: Расходы на резервы
  {
    "id": 501,
    "code": "PROVISION_EXP",
    "name": "Расходы на резервы",
    "type": "sum",
    "query": {
      "metric": "provision_expense"
    }
  }
]
```

#### Метаданные аналитических разрезов

```json
{
  "algorithms": [
    {
      "id": 1,
      "drill_order": [["segment"], ["geo_structure"]]
    },
    {
      "id": 2,  
      "drill_order": [["segment"], ["product"]]
    },
    {
      "id": 3,  
      "drill_order": [["geo_structure"]]
    }
  ],
  "dimensions": [
    {
      "code": "segment",
      "name": "Сегмент",
      "column": "segment"
    },
    {
      "code": "geo_structure",
      "name": "Геоструктура",
      "column": "geo_structure"
    },
    {
      "code": "product",
      "name": "Продукт",
      "column": "product"
    }
  ]
}
```

#### Анализ и формирование набора столбцов

| Шаг | Анализ | Добавляемые столбцы |
|------|---------|-------------------|
| 1 | Обязательные столбцы | `metric`, `rep_dt`, `val_plan`, `val_fact` |
| 2 | Аналитические разрезы (все из `dimensions`) | `segment`, `geo_structure`, `product` |
| 3 | Дополнительные фильтры из `query` | `currency` (из INT_INC) |
| 4 | Объединение требований | Все вышеперечисленные |

#### Итоговая структура таблицы для трех показателей

| Столбец | Тип данных | Обязательный | Источник |
|---------|-----------|--------------|----------|
| `metric` | varchar(50) | Да | Обязательный (идентификатор показателя) |
| `rep_dt` | date | Да | Обязательный |
| `val_plan` | decimal(18, 6) | Да | Обязательный |
| `val_fact` | decimal(18, 6) | Да | Обязательный |
| `segment` | varchar(50) | Да | Аналитический разрез |
| `geo_structure` | varchar(50) | Да | Аналитический разрез |
| `product` | varchar(50) | Да | Аналитический разрез |
| `currency` | varchar(3) | Нет | Дополнительный фильтр (только для INT_INC) |

**Примечания:**
- Столбец `currency` является необязательным (`NOT NULL = false`), так как используется только для одного показателя
- Для показателей, не использующих `currency`, в этом столбце может быть NULL или значение по умолчанию

### Пояснения к данным

- Таблица содержит только самые детализированные записи (сегмент + геоструктура + продукт)
- Все столбцы имеют заполненные значения, отсутствуют тоталы и сабтоталы
- Для факторного анализа используются агрегации на лету:

**Общий итог (рассчитывается программно):**
- План: 1000.00 (сумма всех `val_plan`)
- Факт: 900.00 (сумма всех `val_fact`)
- Отклонение: -100.00

**Разложение по сегментам (рассчитывается программно):**
- UL (Юридические лица): план 600.00 → факт 650.00 (отклонение +50.00) ✓
- FL (Физические лица): план 300.00 → факт 200.00 (отклонение -100.00) ✗
- OTHER (Прочие): план 100.00 → факт 50.00 (отклонение -50.00) ✗

### Примеры запросов для разных уровней детализации

**Уровень 0: Общий итог (агрегация)**
```sql
SELECT metric, rep_dt,
       SUM(val_plan) as plan,
       SUM(val_fact) as fact,
       SUM(val_fact) - SUM(val_plan) as deviation
FROM fa_indicator_data
WHERE metric = 'commission_income_total'
  AND rep_dt = '2026-04-01'
GROUP BY metric, rep_dt;
```

**Уровень 1: По сегментам (агрегация)**
```sql
SELECT segment,
       SUM(val_plan) as plan,
       SUM(val_fact) as fact,
       SUM(val_fact) - SUM(val_plan) as deviation
FROM fa_indicator_data
WHERE metric = 'commission_income_total'
  AND rep_dt = '2026-04-01'
GROUP BY segment;
```

**Уровень 2: По геоструктурам для конкретного сегмента (агрегация)**
```sql
SELECT geo_structure,
       SUM(val_plan) as plan,
       SUM(val_fact) as fact,
       SUM(val_fact) - SUM(val_plan) as deviation
FROM fa_indicator_data
WHERE metric = 'commission_income_total'
  AND rep_dt = '2026-04-01'
  AND segment = 'FL'
GROUP BY geo_structure;
```

## Дополнительные требования

### Хранение только детализированных данных

- Таблица хранит только самые детализированные данные
- Тоталы и сабтоталы по аналитическим разрезам рассчитываются программно с помощью агрегаций (GROUP BY)
- Отсутствуют записи с обобщенными значениями разрезов
