# Требования к структуре данных для факторного анализа

## 1. Общее описание

Система факторного анализа оперирует двумя взаимосвязанными структурами метаданных:

1. **Иерархия показателей** — древовидная структура финансовых показателей, определяющая порядок декомпозиции финансового результата на составляющие компоненты и драйверы.
2. **Алгоритмы разложения по аналитическим разрезам** — набор алгоритмов детализации значений показателей по измерениям (сегмент, геоструктура, продукт, канал продаж и др.).

Обе структуры хранятся в формате JSON и используются для построения интерфейсов и запросов к базе данных при проведении план-фактного анализа.

---

## 2. Структура данных: Иерархия показателей

### 2.1. Формат хранения

Иерархия представлена в виде плоского JSON-массива объектов. Каждый объект описывает один показатель. Древовидная структура формируется через ссылку `parent → id`.

### 2.2. Обязательные поля объекта показателя

| Поле | Тип данных | Обязательность | Описание |
|--|--|--|--|
| `id` | `integer` | Всегда обязательно | Уникальный числовой идентификатор показателя в рамках всей иерархии |
| `code` | `string` | Всегда обязательно | Короткий мнемонический код показателя. Должен быть уникальным в рамках всей иерархии. Допустимые символы: латинские буквы верхнего регистра, цифры и знак подчёркивания |
| `name` | `string` | Всегда обязательно | Человеко-читаемое отображаемое название показателя |
| `parent` | `integer \| null` | Всегда обязательно | Ссылка на `id` родительского показателя. Значение `null` допускается только для корневого узла |
| `type` | `enum("sum", "multi")` | Обязательно для составных узлов | Тип агрегации составного показателя. Отсутствует у листовых узлов |
| `query` | `object` | Условно обязательно (см. п. 2.4) | Параметры фильтрации для получения значений из БД |
| `driverType` | `enum("rate", "base")` | Обязательно для потомков `multi`-узла | Тип драйвера: коэффициент (`rate`) или объёмный показатель (`base`) |

### 2.3. Типы узлов иерархии

#### 2.3.1. Корневой узел

- Единственный узел с `parent: null`.
- Должен иметь `type: "sum"` или `type: "multi"`.
- В иерархии допускается ровно один корневой узел.

#### 2.3.2. Листовой узел

- Узел, на `id` которого не ссылается ни один другой узел через своё поле `parent`.
- Не имеет поля `type`.
- Может иметь поле `query` для получения данных из БД.
- Если поле `query` отсутствует, значение рассчитывается как сумма потомков (при наличии таковых по ссылкам `parent`).

#### 2.3.3. Составной узел типа `sum`

- Показатель, значение которого равно сумме значений его дочерних элементов.
- Дочерние элементы определяются фильтрацией всех узлов по условию `child.parent === node.id`.
- **Без `query`**: значение рассчитывается суммированием дочерних.
- **С `query`**: значение берётся из БД. Значение из БД имеет приоритет над расчётным.

#### 2.3.4. Составной узел типа `multi`

- Показатель, значение которого является произведением драйверов (коэффициента на базу).
- **Обязательно** должен иметь поле `query` — значение из БД необходимо для обратного расчёта ставки (`rate`).
- Все дочерние элементы обязаны иметь поле `driverType`.

### 2.4. Правила наличия поля `query`

| Тип узла | `query` обязательно? | Поведение при отсутствии | Поведение при наличии |
|----------|---------------------|--------------------------|----------------------|
| Лист без `driverType` | Нет | Значение = сумма потомков | Значение берётся из БД |
| Лист с `driverType: "base"` | Нет | Значение = сумма потомков | Значение берётся из БД |
| Лист с `driverType: "rate"` | Нет | Значение рассчитывается обратным счётом: `rate = parent_value / base_sibling_value` | Не применимо (ставка всегда расчётная) |
| `type: "sum"` | Нет | Значение = сумма дочерних | Значение берётся из БД (приоритет над расчётным) |
| `type: "multi"` | **Да** | Недопустимо | Значение берётся из БД, используется для обратного расчёта `rate` |

### 2.5. Формат поля `query`

Поле `query` — это объект произвольной структуры вида «ключ-значение», где:

- **Ключ** (`string`) — имя поля фильтрации (соответствует логическому атрибуту в БД).
- **Значение** — строка (`string`) для единичного значения фильтра либо массив строк (`string[]`) для множественного значения.

Примеры:
```json
{ "metric": "interest_income" }
{ "segment": ["corporate", "sme"] }
{ "metric_type": "other_nii" }
```

Состав допустимых ключей и значений определяется схемой хранения данных в БД и не регламентируется метаданными иерархии.

### 2.6. Обратный расчёт ставки (rate)

Для узлов типа `multi` ставка рассчитывается по формуле:

```
rate_plan = multi_plan / base_plan
rate_fact = multi_fact / base_fact
```

Где:
- `multi_plan`, `multi_fact` — плановое и фактическое значения родительского `multi`-узла, полученные из БД через `query`.
- `base_plan`, `base_fact` — плановое и фактическое значения дочернего узла с `driverType: "base"`, полученные из БД.

## 3. Структура данных: Алгоритмы разложения по аналитическим разрезам

### 3.1. Формат хранения

Корневой JSON-объект содержит два массива:
```json
{
  "algorithms": [...],
  "dimensions": [...]
}
```

### 3.2. Объект аналитического разреза (dimension)

| Поле | Тип данных | Обязательность | Описание |
|------|-----------|----------------|----------|
| `code` | `string` | Да | Уникальный код разреза. Используется как ссылка из поля `drill_order` алгоритмов |
| `name` | `string` | Да | Человеко-читаемое отображаемое имя разреза |
| `column` | `string` | Да | Наименование столбца в таблице БД, содержащего значения данного разреза |

### 3.3. Объект алгоритма разложения

| Поле | Тип данных | Обязательность | Описание |
|------|-----------|----------------|----------|
| `id` | `integer` | Да | Уникальный числовой идентификатор алгоритма |
| `drill_order` | `array<array<string>>` | Да | Упорядоченный массив шагов разложения. Каждый шаг — массив кодов аналитических разрезов |

### 3.4. Семантика `drill_order`

- Массив `drill_order` определяет последовательность шагов детализации данных.
- Каждый элемент массива (шаг) — это массив из одного или нескольких кодов аналитических разрезов.
- **Один код в шаге** — детализация по одному измерению (например, `["segment"]`).
- **Несколько кодов в шаге** — детализация по пересечению измерений (например, `["geo_structure", "product"]` — группировка одновременно по обоим).
- Разложение выполняется рекурсивно: результат шага N является входом для шага N+1.

### 3.5. Ссылочная целостность

- Все значения кодов в `drill_order` должны присутствовать в массиве `dimensions` (совпадение по полю `code`).
- Код разреза может использоваться в нескольких алгоритмах и на разных шагах.

## 4. Правила валидации

### 4.1. Валидация иерархии показателей

#### Структурные правила

1. В массиве должен существовать ровно один узел с `parent: null` (корень).
2. Все значения `id` должны быть уникальными целыми числами.
3. Все значения `code` должны быть уникальными строками.
4. Для каждого узла с `parent != null` должен существовать узел с соответствующим `id` (целостность ссылок).
5. Граф, образованный связями `parent → id`, не должен содержать циклов.
6. Каждый узел, имеющий дочерние элементы (на него ссылаются через `parent`), должен иметь поле `type`.

#### Правила по типам узлов

7. Узел с `type: "multi"` обязан иметь поле `query`.
8. Все дочерние элементы узла с `type: "multi"` обязаны иметь поле `driverType` со значением `"rate"` или `"base"`.
9. Дочерние элементы узла с `type: "sum"` не должны иметь поле `driverType`.
10. У узла с `type: "multi"` должен быть ровно один дочерний элемент с `driverType: "rate"` и ровно один с `driverType: "base"`.
11. Узел с `driverType: "rate"` не должен иметь поле `query` (значение всегда вычисляется обратным счётом).

#### Правила значений полей

12. Поле `code` должно соответствовать шаблону `^[A-Z0-9_]+$`.
13. Поле `id` должно быть положительным целым числом.
14. Поле `name` не должно быть пустой строкой.

### 4.2. Валидация алгоритмов разложения

#### Структурные правила

15. Все значения `id` алгоритмов должны быть уникальными целыми числами.
16. Массив `drill_order` должен содержать хотя бы один шаг.
17. Каждый шаг в `drill_order` должен содержать хотя бы один код разреза.
18. Все коды в `drill_order` должны ссылаться на существующие записи в массиве `dimensions` (по полю `code`).

#### Правила справочника разрезов

19. Все значения `code` в массиве `dimensions` должны быть уникальными строками.
20. Поле `column` в массиве `dimensions` должно быть непустой строкой.
21. Один и тот же код разреза не должен повторяться в рамках одного алгоритма (в пределах всех шагов `drill_order`).

## 5. Ограничения и зависимости между структурами

### 5.1. Связь показателей и алгоритмов разложения

- Алгоритмы разложения являются **универсальными** — они не привязаны к конкретным показателям и могут применяться к любому показателю из иерархии.
- Привязка конкретного алгоритма к конкретному показателю определяется внешней конфигурацией (не входит в описанные метаданные).

### 5.2. Ограничение на разложение драйверов

- Показатели с полем `driverType` (драйверы узлов типа `multi`) **не могут** быть разложены по аналитическим разрезам отдельно от своего родительского показателя.
- Разложение по аналитическим разрезам применяется к `multi`-показателю целиком, а значения драйверов пересчитываются для каждой ячейки разложения.

### 5.3. Приоритет источников данных

Для показателей, имеющих поле `query`:
1. Значения из БД (через `query`) имеют приоритет над расчётными значениями.
2. Если данные в БД отсутствуют для конкретной комбинации фильтров, используется расчётное значение (сумма потомков для `sum`, произведение для `multi`).

## 6. Модель данных в БД (требования к таблице фактов)

### 6.1. Минимальные требования к таблице хранения данных

На основании описанных метаданных, таблица хранения фактических и плановых значений должна содержать как минимум следующие столбцы:

| Столбец | Тип | Назначение |
|---------|-----|-----------|
| Идентификатор показателя / метрики | `string` | Связь с полями из `query` |
| Отчётная дата | `date` | Период, за который собираются данные |
| Плановое значение | `numeric` | Значение плана |
| Фактическое значение | `numeric` | Значение факта |
| Столбцы аналитических разрезов | по одному на каждый `dimension` | Значения измерений для группировки и фильтрации |

### 6.2. Столбцы аналитических разрезов

Для каждого объекта из массива `dimensions` в таблице БД должен существовать столбец с именем, указанным в поле `column`:

| Разрез (`code`) | Столбец в БД (`column`) | Тип | Назначение |
|-----------------|-------------------------|-----|-----------|
| `segment` | `segment_id` | `string` / `integer` | Идентификатор сегмента |
| `geo_structure` | `geo_structure_id` | `string` / `integer` | Идентификатор геоструктуры |
| `product` | `product_id` | `string` / `integer` | Идентификатор продукта |
| `sales_channel` | `channel_id` | `string` / `integer` | Идентификатор канала продаж |
| `client_type` | `client_type_id` | `string` / `integer` | Идентификатор типа клиента |
| `currency` | `currency_code` | `string` | Код валюты |

## 7. Алгоритм рекурсивного разложения (спецификация поведения)

### 7.1. Общая последовательность

1. **Вход**: показатель + алгоритм разложения + (опционально) фильтры от предыдущих шагов.
2. **Шаг N** (для каждого шага из `drill_order`):
   - Формируется SQL-запрос с группировкой по столбцам, указанным в текущем шаге.
   - Применяются фильтры из предыдущих шагов (значения разрезов, выбранные на более ранних уровнях).
   - Результат: набор записей с агрегированными значениями (план, факт, отклонение) по каждой комбинации значений текущих разрезов.
3. **Переход к шагу N+1**: для каждой полученной записи (каждой комбинации значений разрезов) выполняется следующий шаг с добавлением текущих значений в фильтры.

### 7.2. Формирование SQL-запроса для одного шага

Для шага с кодами разрезов `[dim1, dim2, ...]`:
- **GROUP BY**: столбцы `dim1.column, dim2.column, ...`
- **WHERE**: фильтры из `query` показателя + фильтры из предыдущих шагов
- **SELECT**: столбцы группировки, `SUM(plan_value)`, `SUM(fact_value)`, отклонение

### 7.3. Условия остановки

- Если текущий шаг — последний в `drill_order`, рекурсия завершается.
- Если на текущем шаге результат пуст, дальнейшая детализация не выполняется.

## 8. Примеры корректных и некорректных данных

### 8.1. Корректная иерархия (минимальный пример)

```json
[
  { "id": 1, "code": "TOTAL", "name": "Итого", "parent": null, "type": "sum" },
  { "id": 2, "code": "INCOME", "name": "Доход", "parent": 1, "query": { "metric": "income" } },
  { "id": 3, "code": "EXPENSE", "name": "Расход", "parent": 1, "query": { "metric": "expense" } }
]
```

### 8.2. Корректный `multi`-узел с драйверами

```json
[
  { "id": 10, "code": "INT_INC", "name": "Процентный доход", "parent": 1, "type": "multi", "query": { "metric": "interest_income" } },
  { "id": 11, "code": "RATE", "name": "Ставка", "parent": 10, "driverType": "rate" },
  { "id": 12, "code": "VOLUME", "name": "Объём", "parent": 10, "driverType": "base", "query": { "metric": "volume" } }
]
```

### 8.3. Некорректные данные (ошибки валидации)

**Ошибка: `multi`-узел без `query`**
```json
{ "id": 10, "code": "INT_INC", "name": "Процентный доход", "parent": 1, "type": "multi" }
// ← Нарушение правила 7: type: "multi" обязан иметь query
```

**Ошибка: дочерний элемент `multi` без `driverType`**
```json
{ "id": 11, "code": "RATE", "name": "Ставка", "parent": 10 }
// ← Нарушение правила 8: потомок multi-узла обязан иметь driverType
```

**Ошибка: битая ссылка `parent`**
```json
{ "id": 5, "code": "X", "name": "Неизвестный", "parent": 999 }
// ← Нарушение правила 4: узел с id=999 не существует
```

**Ошибка: неизвестный код разреза в `drill_order`**
```json
{ "id": 1, "drill_order": [["unknown_dimension"]] }
// ← Нарушение правила 18: код "unknown_dimension" отсутствует в dimensions
```

## 9. Расширяемость

### 9.1. Добавление новых показателей

Для добавления нового показателя достаточно добавить новый объект в плоский массив иерархии с корректным `parent`, указывающим на существующий `id`. Изменение кода приложения не требуется.

### 9.2. Добавление новых аналитических разрезов

Для добавления нового разреза необходимо:
1. Добавить объект в массив `dimensions` с уникальным `code` и соответствующим `column`.
2. Обеспечить наличие соответствующего столбца в таблице БД.
3. При необходимости — добавить или обновить алгоритмы в массиве `algorithms`.

### 9.3. Добавление новых алгоритмов разложения

Для добавления нового алгоритма достаточно добавить объект в массив `algorithms` с уникальным `id` и корректным `drill_order`, ссылающимся на существующие коды разрезов.
